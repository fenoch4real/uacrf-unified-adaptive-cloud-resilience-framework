# Sample data (NOT real telemetry)

Everything under this directory is synthetic and exists only so the UI and
integration tests can show a near-complete estate before real collectors are
accepted. Nothing here is provider inventory or accepted evidence, and nothing
may be used as proof of real system behavior. All of it is generated by Java
(module `sample-data-tools`); there is no other language in the tooling.

| Path | Purpose |
| --- | --- |
| `connections/sample-local-estate.json` | A `SAMPLE_LOCAL` connection, six source bindings and a delivery log, including deliberate faults |
| `connections/sample-multicloud-estate.json` | AWS-, Azure- and Google Cloud-shaped feeds ingested through a `SAMPLE_LOCAL` connection: individual collector-shaped inventory observations, provider-shaped metric payloads, separately retained simulated inventory response pages (`NextToken`, `$skipToken`, `nextPageToken`), throttling / permission-denied outages, metric gaps and deliberate faults, plus a per-provider capability matrix |
| `graph/sample-multicloud-graph.json` | A fictional "Meridian Retail" graph that uses all 58 node labels and all 55 relationship types of `design/technical-approach/data-dictionary`. Every record is `SYNTHETIC_FIXTURE`; Authorization, Execution and agent signature records are void or simulated so they can never be mistaken for executable permits |

The real AWS, Azure and GCP connection types stay `UNACCEPTED` and cannot be
bound; the multi-cloud fixture only imitates their payload shapes. Provider
capabilities are declared per provider and never treated as equivalent.

Use these labeled fixtures to continue local application and integration work
while live cloud checks are deferred. They represent a fictional estate, not a
measurement of any real account, and the UI prototype and connected service
flows must not be assumed to have identical coverage. Inventory deliveries use
the current collectors' individual-resource payload fields; the separately
retained response pages simulate provider pagination and are not submitted as
observations. AWS sample observation timestamps match their Config capture
times. Fixture metrics and graph
relationships do not imply that live metric collectors, relationship
discovery, or every application view have been implemented. Expand or adapt
the fixtures when needed, but keep sample provenance visible and do not treat
sample observations as qualified provider evidence.

The [connections live-check guide](../services/connections/README.md#deferred-live-provider-checks)
records the account setup and validation work to return to later.

Each delivery carries an `expect` value (`ACCEPTED`, `DUPLICATE` or
`QUARANTINED:<reason>`) that the S03 integration tests assert after posting the
deliveries in order.

The browser's read-only connections and inventory views can display observations
once they have been ingested through authorized S03 APIs. The application does
not automatically load this fixture, and a browser-driven importer is not yet
implemented. Seeing these views does not establish a live provider connection
or evidence qualification.

## Regenerating

The tests fail when a committed file differs from what the generators produce,
and validate the graph against the data dictionary (labels, relationship types,
required and common properties, snake_case, no persisted aliases, endpoint
roles, cardinality, uniqueness, tenant scope).

```
./mvnw -pl sample-data test                                  # verify
./mvnw -pl sample-data test -Duacrf.sample.regenerate=true   # rewrite the JSON
```
